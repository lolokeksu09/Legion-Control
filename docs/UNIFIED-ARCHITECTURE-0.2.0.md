# Legion Control 0.2.0 — Unified Architecture

**Статус:** утверждённое направление владельца; рабочий план, не реализованный релиз.
**Дата:** 26.11.2026.
**База:** `867ed8ca671a243c63b9b961c4ea6442a7b32947`, alpha.59. [Android CI](https://github.com/lolokeksu09/Legion-Control/actions/runs/45878745506) и [подписанная сборка](https://github.com/lolokeksu09/Legion-Control/actions/runs/45878745611) успешны на этой ревизии; эмулятор пропущен. Физическая приёмка не подтверждена.
**Источник решения:** замечание владельца по пяти вкладкам установленного приложения: слишком много функционально связанных, но самостоятельных экранов. Одобрено проектирование реального объединения, а не переименования карточек. Название и версия 0.2.0 — целевой ориентир; номер сборки/тег сейчас не меняются.

## 1. Цель и границы

Перевести приложение от каталога отдельных утилит к пяти предметным центрам. Пользователь выбирает **игру, сессию, устройство или задачу**, а не название внутреннего модуля. Единый источник данных, согласованные состояния и общая навигация должны устранять повторное выполнение действий и чтение одних и тех же данных.

Не засчитывать как реализацию:
- переименование/группировку карточек с прежним набором раздельных экранов;
- экран-меню, который лишь открывает прежние Activity без переноса пользовательского контекста;
- дублирование репозитория, хранилища, сборщика измерений или логики экспорта ради нового экрана;
- скрытие старой функции без эквивалентного рабочего пути;
- выдуманные показатели, автоматические «оптимизации», фиктивные FPS, новые разрешения без отдельного основания.

Сохраняются Kotlin + Android Views/Fragments + AndroidX Navigation/Lifecycle, Rust/JNI, один Gradle-модуль :app на первом этапе, существующие SQLite и SharedPreferences. Compose, DI-фреймворк, полная смена стека и механическое дробление на Gradle-модули не входят в объём. Сохраняются package ID `dev.lolokeksu.legioncontrol`, ключ подписи, пользовательские записи, разрешения, согласие MediaProjection, штатные документ-пикеры, bounded Replay и foreground-only monitor. Отдельно одобренный Shizuku (shell UID 2000) остаётся опциональным и ограниченным существующими безопасными операциями.

## 2. Снимок текущей архитектуры

- `HubToolCatalog.kt`: 18 уникальных видимых инструментов после объединения Live Monitor. `HubPageFragment.kt`: 5 вкладок и контекстные маршруты. `FeatureFinder.kt`: 80 стабильных идентификаторов функций, 21 логическая категория; это не количество экранов.
- `MainActivity.kt` и `LiveMonitorActivity.kt`: диагностический центр с четырьмя страницами и встраиваемым LiveMonitorPanel. Legacy Activity перенаправляет. История SQLite и временные точки Live Monitor различаются по сроку хранения; их нельзя смешивать.
- `CaptureStudioActivity.kt`, `CaptureStudioViewModel.kt`, `CaptureStudioRepository.kt`: объединённое управление захватом и медиатекой; существуют независимые режимы записи, Replay и скриншотов.
- `GameSessionRepository.kt` уже общий владелец сохранённых игровых сессий; отдельные SessionLibrary/Compare/Signals/Baselines/Incidents ViewModel создают самостоятельные состояния выбора и запросов. Это главный кандидат на консолидацию пользовательского потока.
- `GameLaunchProfileEditor.kt` уже общий редактор профиля; `SystemControlPanel.kt`, `CapabilityAccessBackend.kt` и `ResourceTelemetryBackend.kt` — действующие точки повторного использования. Не создавать альтернативные реализации этих владельцев.
- Исторические ограничения и незакрытые риски из [AUDIT](AUDIT-2026-11-26.md) и [Stability & Safety](STABILITY-SAFETY-2026-11-26.md) сохраняются, пока не закрыты доказательствами. Новый план заменяет прежнюю цель сохранять отдельный интерфейс каждого Lab, но не отменяет контракт безопасности.

## 3. Целевая информационная архитектура

Пять вкладок: **Главная / Игры / Система / Аналитика / Настройки**. Технические ключи старых вкладок tools/history и стабильные маршруты сохраняются как алиасы, если это нужно для обратной совместимости. На этапе миграции можно оставить прежние подписи до готовности соответствующего центра. Медиацентр и периферия доступны с Главной и Системы; отдельные нижние вкладки им не требуются.

| Центр | Основной пользовательский путь | Что объединяется |
|---|---|---|
| Игровой | Игры → карточка конкретной игры → подготовка → запуск/сессия → результаты | Game Toolbox, Smart Profiles, Game Preflight, Game Session, Application Center (игровой контекст) |
| Аналитика | Выбор игры/сессии один раз → обзор → графики, события, проблемы, сравнения, экспорт | Session Library, Session Compare, Session Signals, Session Baselines, Session Incidents, Experiment Lab |
| Устройство | Система → обзор → ресурсы / батарея / тепло / сеть / аппаратные тесты / совместимость | текущий диагностический центр, Gaming Lab, Hardware Lab, Compatibility Lab, Connectivity Observatory |
| Периферия | Система → Экран и управление → дисплей / сенсор / звук / вибрация / контроллеры | Display Patterns, Audio Lab, Haptic Lab, Gamepad Live и соответствующие тесты Gaming/Hardware/Compatibility |
| Медиа | Главная → Медиацентр → захват / настройки / библиотека | Capture Studio, Replay, скриншоты, MP4/PNG, редактирование/экспорт |
| Настройки (общая инфраструктура, не шестой предметный центр) | Настройки → разрешения / параметры Android / данные / диагностика доступа | существующие CapabilityAccessBackend, SystemControlPanel, Shizuku, backup/restore |

Application Center продолжает поддерживать неигровые приложения, историю версий, заметки и управление библиотекой; эти функции не должны исчезнуть при объединении игрового контекста. Experiment Lab сохраняет произвольные A/B-эксперименты и заметки, включая не привязанные к игровой сессии.

### Канонические владельцы данных

| Область | Источник сейчас | Целевой принцип |
|---|---|---|
| Игры / приложения | HubRepository, ApplicationCenterRepository, ToolboxGameSelection | единая идентичность packageName; один владелец каждого поля; общий контекст, без копирования избранного/заметок/профиля |
| Профили запуска | GameLaunchProfiles, GameLaunchProfileEditor, SmartProfilesRepository | редактор и репозиторий по назначению; различать профиль запуска и правила авто-профилей; единый путь применения и возврата |
| Игровые сессии | GameSessionRepository, GameSessionRecorderService | session ID и packageName проверяются; единая выборка для активного контекста, общий слой отчётов; сервис остаётся владельцем записи |
| Ресурсы устройства | ResourceTelemetryBackend, DeviceInsights, GameSessionTelemetry, RustSampleController | общий источник измерений и метаданных качества; один активный capture для конфликтующих проверок; разные интервалы/семантика сохраняются |
| Диагностическая история | LocalHistoryStore, DiagnosticsHistoryRepository | явные виды записей и их источники; не сохранять временный мониторинг в SQLite без отдельной функции/решения |
| Медиа | CaptureStudioRepository, CaptureCoordinator, существующие сервисы захвата | один координатор состояния, единая библиотека с раздельными режимами и владением файлами |
| Разрешения / системные изменения | CapabilityAccessBackend, SystemControlPanel, существующая логика применения/rollback | единое состояние возможностей; проверка при выполнении; общий арбитр конфликтующих изменений до расширения автоматизации |

## 5. План исполнения крупными вертикальными срезами

Основной порядок: сначала функциональный контекст и слой данных, затем объединённый экран и визуальное уплотнение. Каждая фаза должна дать реально работающий путь; не дробить на бессмысленные косметические коммиты. Новые названия классов ниже описывают предполагаемые роли, а не существующие API. Перед правкой подтвердить вызовы и зависимости конкретного HEAD.

### Фаза A — карта функций и единая аналитика (UA-01–04, UA-12)

Первый большой патч. До изменений сравнить точные границы чтения, порядок событий, лимиты и фильтры в `GameSessionRepository.kt`, `SessionLibraryViewModel.kt`, `SessionCompareViewModel.kt`, `SessionSignalsViewModel.kt`, `SessionBaselinesViewModel.kt`, `SessionIncidentsViewModel.kt`, `ExperimentLabViewModel.kt`. Сохранить чистые вычислители `GameSessionAnalysis.kt`, `SessionCompareAnalysis.kt`, `SessionSignals.kt`, `SessionBaselines.kt`, `SessionIncidents.kt`, `ExperimentAnalytics.kt`.

1. Составить таблицу фактических feature ID и маршрутов; добавить стабильный общий контекст (packageName, sessionId, период, сравниваемая пара). Выбор второй сессии не меняет основную. Не выдумывать данные для незавершённых/пустых сессий.
2. Объединить совместимые чтения в bounded snapshot/read model. Использовать текущий репозиторий, пагинацию, cancellation/generation и идентичность запроса. Для разных аналитических выборок сохранять необходимые пределы и фильтры; не превращать 10000 точек и 2000 событий в безусловную загрузку всей истории.
3. Единый Analytics host: библиотека/выбор → обзор → хронология и инциденты → базовые показатели/сравнение → экспорт и эксперименты. Выбор сохраняется при переключении; диалоги выбора используются только для смены контекста.
4. `HubPageFragment.kt`, `HubToolCatalog.kt`, `FeatureFinder.kt`, `FeatureReveal.kt`, `HubDestinationRoutes.kt`, nav graph: заменить разрозненные первичные входы на центр; legacy маршруты перенаправляют с контекстом, пока совместимость нужна. Перепроверить инструментальные тесты.
5. Приёмка: выбрать A → быстро выбрать B → открыть события/инциденты → сравнить B с подходящей C → экспортировать выбранный отчёт; пустая/удалённая/незавершённая сессия, отмена SAF, поворот, Back, пропущенная телеметрия, несовпадение packageName.

**Выход:** нет шести независимых первичных аналитических экранов; функциональный выбор и связанные данные действительно общие.

## 6. Обязательные инварианты миграции

- Не удалять таблицы, записи, настройки, ключ подписи или внешние действия. Перед необходимой миграцией — проверка схемы и данных, fixture старой версии, идемпотентность, план восстановления; необратимое изменение требует отдельного решения владельца.
- Старые экраны можно удалить из пользовательской навигации только после подключения всех их функций, проверки ссылок/Intent/feature ID и обновления тестов. До этого — совместимый адаптер, не второй набор бизнес-логики.
- Не делать один огромный ViewModel. Общий выбор/контекст на уровне центра, специализированные bounded состояния вычислений и независимые операции — по областям ответственности. Не хранить Activity/View в долгоживущем ViewModel.
- У каждого read/write/export есть identity, lifecycle, отмена и ясный failure path. Экспорт привязан к конкретному подтверждённому снимку, а не текущему изменившемуся фильтру.
- Любая настройка Android, удаление медиа или импорт архива требует существующего явного действия и проверки соответствующих возможностей. Не разрешать поиск автоматически выполнять операции.

## 7. Проверки, поставка и правила сопровождения

На каждом срезе:
1. Зафиксировать базовый SHA, реестр функций/маршрутов и связанные source guards **до** изменения. Проверить не только новый скрипт, но и исторические проверки изменяемой области. Случаи с фиксированными счётчиками инструментов/кнопок уже дважды ломали CI; заменить их только на более содержательный контракт полного набора действий и маршрутов.
2. Добавить целевые JVM/regression tests для общих моделей и identity/cancellation, сохранить проверки безопасности, миграций, Rust JNI, медиа и подписи. Запускать `python3 scripts/run_source_checks.py` целиком в доступном окружении. Если локально нет доступа к репозиторию/SDK — использовать CI и не выдавать сравнение строк за выполнение Python/JVM.
3. Обязательные gates проекта: workflow Android Kotlin + Rust, unit (`testDebugUnitTest`), сборка/lint, проверка APK, SQLite/OSV и подписанная сборка согласно действующим workflow. Сверить точные шаги в [.github/workflows/android.yml](../.github/workflows/android.yml) и релизном workflow при реализации.
4. По действующей политике быстрых итераций полная эмуляторная проверка не запускается без необходимости; отметить NOT RUN. Для критических сценариев обновления, восстановления, consent, реальных измерений и окончательного 0.2.0 — отдельно зафиксировать требуемую физическую/целевую приёмку или разрешённое исключение по [TESTING-LEVELS](../TESTING-LEVELS.md). Не считать CI доказательством реального оборудования.
5. Сливать согласованный функциональный срез в main в рамках разрешения владельца; перед заявлением «готово» подтвердить exact-SHA Android CI и подписанный артефакт. При сбое — исправить причину и повторить gate, а не добавлять новый функционал поверх красной сборки. При конфликте HEAD не перезаписывать изменения. Публикация нового релиза отдельна от получения подписанного APK.

### C2 — вкладка «Система» (#95)

- Ресурсы, сеть, аппаратные тесты, датчики, батарея и история открывают конкретную страницу диагностического центра. Звук и вибрация открывают встроенные лаборатории. Экран и геймпад используют существующие полноэкранные проверки. Поиск раскрывает нужный контрол без старта замера.
